# Отчёт о восстановлении сборки и симулятора

Дата: 2026-11-01

## Краткий итог

- Исправлены несовместимые pins пяти Git submodules. `Makefile` менять не
  потребовалось.
- Проверены обязательные патчи проекта.
- Собраны все пять вариантов из CI matrix: MIPS Material, MIPS Z-Bolt,
  MIPS small-screen, ARM и simulator.
- В fake Moonraker добавлена динамика нагрева и охлаждения сопла и стола с
  гистерезисом. Поведение проверено локально по WebSocket.
- Добавлен `tools/run-simulator.sh`: он запускает simulator с fake Moonraker на
  loopback, проверяет адрес и порт, пишет логи и останавливает fake при выходе.
- Один пользовательский запуск launcher завершился с кодом 134. По журналам
  simulator подключился к fake и отправил команды нагрева, но точная причина
  завершения не установлена.

## Исходное состояние

Закреплённые версии зависимостей разошлись с API и патчами, которые использует
проект:

| Подмодуль | Было в рабочем дереве | Выставлено для сборки |
| --- | --- | --- |
| `lvgl` | 10.0.0 development | `v8.4.0-41-gb0c4cb36b` |
| `lv_drivers` | более новая master-ревизия | `v8.3.0` |
| `libhv` | `v1.3.4-64-g060a4b6` | `v1.3.4` |
| `mbedtls` | 4.2.0 development | `mbedtls-3.6.7` |
| `spdlog` | более новая v1.x-ревизия | `v1.12.0-47-gddce4215` |

LVGL 10 и mbedTLS 4 не совместимы с текущими исходниками проекта и
интеграцией libhv. Патчи для `lvgl`, `lv_drivers` и `spdlog` не применялись к
новым ревизиям. Новая ревизия libhv также не содержала `hconfig.h`, который
ожидает существующий Makefile после очистки.

## Что изменено

1. Выставлены проверенные совместимые pins подмодулей, перечисленные выше.
   После этого все четыре патча из `patches/` применяются или распознаются как
   уже применённые через `scripts/apply-patches.sh`.
2. Существующее локальное изменение `libhv/ssl/mbedtls.c` сохранено. Оно
   обрабатывает CA bundle в TLS backend и не было заменено при смене pin.

Проверка WSL показала, что процессы Klipper/Moonraker, systemd units и их
конфиги там отсутствуют. Для UI-проверки поэтому выбран fake Moonraker, который
работает только на loopback и не требует Klipper или реального принтера.
3. В `tools/fake_moonraker.py` добавлена тепловая модель для `extruder` и
   `heater_bed`. Fake обрабатывает `SET_HEATER_TEMPERATURE`, `M104`, `M109`,
   `M140`, `M190` и `TURN_OFF_HEATERS`, изменяет target и отправляет обновления
4. Нагрев идёт с конечной скоростью; при достижении верхней границы
   гистерезиса мощность выключается, при остывании до нижней границы включается
   скорость нагрева сопла 5 C/с, стола 1 C/с; охлаждение 1 C/с и 0.25 C/с
   соответственно. Значения можно переопределять CLI-параметрами fake.
   направленным не на `127.0.0.1:7125`, и если порт уже занят. Он запускает
   fake Moonraker с cold-start 25/0 C и bowl mesh, пишет журналы в
   Klipper/Moonraker не запускаются, соединения с принтером нет.
6. `AGENTS.md` дополнен инструкциями по launcher и тепловой модели.

## Ошибки, найденные при восстановлении

- Обычный MIPS build сначала останавливался с `Toolchain missing`. После этого
  установлены закреплённые toolchains MIPS и ARM через
  `scripts/setup-toolchain.sh`.
- Первый запуск `scripts/build.sh sim` завершался на сообщениях, что патчи
  `0001-lv_driver_fb_ioctls.patch`, `0002-spdlog_fmt_initializer_list.patch` и
  `0003-lvgl-dpi-text-scale.patch` не применяются к текущим pins.
- Первая чистая MIPS-сборка на неподходящей ревизии libhv остановилась с
  `fatal error: hconfig.h: No such file or directory`. Pin libhv возвращён на
  `v1.3.4`; после этого сборка прошла.
- При последующем пользовательском запуске `tools/run-simulator.sh` оболочка
  сообщила exit code 134. В `build/bin/guppyscreen.log` нет явного `abort`,
  assertion или exception; `coredumpctl` и core-файл недоступны. Журналы
  подтверждают, что simulator подключился к fake и отправлял ему команды
  изменения target. Поэтому причина кода 134 остаётся неустановленной и
  требует повторного воспроизведения под debugger, если проблема повторится.

## Результаты сборок

Все сборки запускались через `scripts/build.sh`, как и в GitHub Actions
workflow. Размеры ниже относятся к локальным бинарникам сборки, не к
release-артефактам после упаковки/strip.

| Вариант | Результат |
| --- | --- |
| `scripts/build.sh mips --clean` | Успех, 8,810,352 байта |
| `scripts/build.sh mips zbolt` | Успех, 8,810,248 байт |
| `scripts/build.sh mips --small` | Успех, 8,351,572 байта |
| `scripts/build.sh arm --clean` | Успех, 25,634,640 байт |
| `scripts/build.sh sim` | Успех, 9,204,104 байта |

MIPS ELF проверен как ELF32 little-endian `EXEC`, flags `0x50001007`, без
`INTERP`/`DYNAMIC`. ARM ELF проверен как AArch64 `EXEC`, также без
`INTERP`/`DYNAMIC`. Simulator собран как x86-64 PIE и использует системную
SDL2 2.32.10. Автоматически созданный `build/bin/guppyconfig.json` прошёл
проверку JSON.
Все targets используют один путь `build/bin/guppyscreen`; после последней
сборки по нему находится x86-64 simulator.

## Проверки тепловой модели

Локальный WebSocket-тест без GUI и без принтера подтвердил:

- target сопла 70 C изменил температуру с 25 C до 30 C за первый интервал;
- target стола 45 C изменил температуру с 25 C до 26 C;
- у обоих объектов мощность переключалась между 0 и 1 у заданной цели;
- `M109` и `M190` устанавливают target, `TURN_OFF_HEATERS` сбрасывает оба
  target в 0 C.

`python3 -m py_compile tools/fake_moonraker.py`, `bash -n tools/run-simulator.sh`
и проверка `tools/run-simulator.sh --help` прошли. После интеграционных тестов
fake завершён, порт 7125 свободен.

## Текущее состояние Git и ограничения

- Обновления submodule pointers для `libhv`, `lv_drivers`, `lvgl`, `mbedtls` и
  `spdlog` добавлены в index, но коммит не создан.
- Применённые patch-файлы внутри подмодулей оставлены незастейдженными,
  согласно правилам репозитория. Локальная CA-правка в libhv также сохранена.
- `AGENTS.md` и `tools/fake_moonraker.py` изменены, новый
  `tools/run-simulator.sh` добавлен; эти изменения не застейджены.
- Fake WPA не запускается из `tools/run-simulator.sh`; Wi-Fi panel требует
  отдельного `tools/fake_wpa_supplicant.py` и настройки socket path.
- Наблюдавшийся exit code 134 не удалось объяснить по имеющимся логам. Это не
  отменяет успешную сборку simulator и успешные проверки fake protocol, но
  ручной интерактивный runtime следует считать неполностью подтверждённым до
  повторной проверки после пользовательского воспроизведения.
